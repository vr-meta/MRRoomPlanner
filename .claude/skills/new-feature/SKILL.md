# Процесс новой фичи (MRRoomPlanner)

Порядок обязателен: **документ → чек-лист → план → код → тесты → дока → коммит**.
Код раньше документа не писать.

## 1. Разведка (перед любым текстом)

- `docs/CHECKLIST.md` — что уже сделано/в работе; нет ли этой фичи в другом потоке.
- `docs/design/README.md` — индекс решений; профильный док фичи, если есть.
- `docs/design/12-coding-rules.md` — свод правил кода (обязателен).
- `docs/design/14-modularity.md` — **карта владения файлами**: убедиться, что не
  влезаешь в файлы параллельного потока. Общие точки (реестр в `ToolManager.Start`,
  `SetupPalette`, `10-controls.md`) правятся минимально и в последнюю очередь.

## 2. Документ (до кода)

- Новый модуль → новый `docs/design/NN-<slug>.md`: модель данных, подход (параметрика,
  без CSG), UX, скелет классов, что осознанно откладываем.
- Существующий модуль → обновить его док (не плодить дубли).
- Добавить строку в индекс `docs/design/README.md`.

## 3. Чек-лист (до кода)

- В `docs/CHECKLIST.md` — раздел/подраздел фичи с декомпозицией на шаги (M1/B1-стиль:
  каждый шаг = проверяемый результат + тесты). Крупную задачу без декомпозиции не вести.
- Отмечать по ходу: `[~]` начал, `[x]` только когда тесты зелёные.

## 4. Реализация (по шагам декомпозиции)

- **Чистая логика → `RoomPlanner.Core`** (без Unity-зависимостей кроме математики) —
  юнит-тестируемо. Устройство-зависимое — в контроллере (`RoomPlanner.App`).
- **Новый инструмент** = `XxxController : ITool` (Id/PaletteLabel/GetSettings-схема) +
  `Editor/Setup/SetupXxxTool.cs` + одна строка в реестре `ToolManager.Start` + позиция
  в `SetupPalette`. Настройки — только через `SettingsSchema`, `InspectorPanel`/
  `MenuAction` не трогать.
- Объекты сцены регистрировать в `SceneModel`; правки — командами (undo). Правила 12:
  `IsAlive` вместо null-проверок интерфейсных ссылок, winding наружу, ноль аллокаций
  в пер-кадровых путях, драг = transform-превью + один rebuild, ассеты в Setup —
  мутировать без смены GUID.
- Изменил раскладку ввода → синхронно обновить `docs/design/10-controls.md`.

## 5. Проверка результата (до отчёта пользователю)

Единая точка — драйвер (сам выбирает мост/batchmode):

```
node .claude/skills/run-mrroomplanner/driver.mjs status   # компиляция чистая?
node .claude/skills/run-mrroomplanner/driver.mjs test All # EditMode + PlayMode
node .claude/skills/run-mrroomplanner/driver.mjs setup    # ТОЛЬКО если менялся состав рига
node .claude/skills/run-mrroomplanner/driver.mjs build    # APK при необходимости
```

- Изменился **состав рига** (компоненты/сериализованные поля/префабы/панели) →
  обязателен `setup` (batchmode, редактор закрыт) ДО прогона Play-тестов.
- Новая логика — с тестами; исправленный баг — с регрессионным тестом. Play-тесты —
  на реальных компонентах, не на дублях. Маскирующие допуски запрещены.
- Готово = **все тесты зелёные** + компиляция чистая. Про мост помнить: PlayMode через
  мост ненадёжен — редактор закрыть и гнать batchmode.
- Что нельзя проверить headless (вид панелей, жесты) — явно указать в отчёте и
  оставить пункт «проверка на устройстве» в чек-листе.

## 6. Синхронизация доки (вместе с последним коммитом)

- Чек-лист: отметки `[x]`, оставшиеся хвосты — явными пунктами.
- Дизайн-док фичи: привести к фактически реализованному (решение изменилось — обновить).
- Если по ходу выработано новое правило кода — добавить в `12-coding-rules.md`.

## 7. Коммит

- После зелёных тестов: `git add` только своих файлов (чужие незакоммиченные потоки —
  не включать), содержательное сообщение (что и почему, номера шагов, итоги тестов).
- Push — если пользователь не сказал иного.
