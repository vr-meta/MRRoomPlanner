# 29 — Материалы объектов: одеваем импорт из IFC (issue #124)

Вопрос со шлема 2026-08-15: «можно ли импортировать мебель из IFC сразу с текстурами?»
Короткий ответ — **нет, потому что их там нет**. Длинный — ниже: что реально лежит в
экспорте Revit, что мы из этого теряем сегодня и как одеть импорт нашим же CC0-каталогом.

## 1. Что реально приезжает из Revit (замер, `Project1 (2) (2).ifc`, IFC2X3, Revit 24)

| сущность | шт. |
|---|---|
| `IfcStyledItem` | 521 |
| `IfcSurfaceStyle` / `IfcSurfaceStyleRendering` | 36 / 36 |
| `IfcColourRgb` | 64 |
| `IfcMaterial` | 37 |
| `IfcMaterialDefinitionRepresentation` | 36 |
| **`IfcImageTexture` / `IfcSurfaceTexture` / `IfcBlobTexture` / `IfcPixelTexture` / `IfcTextureMap`** | **0 / 0 / 0 / 0 / 0** |

Стандарт IFC текстуры **умеет**; Revit их **не пишет** — экспортируется только
`IfcSurfaceStyleRendering` с одним `IfcColourRgb`. Поэтому «импорт с текстурами» — это
всегда наша работа на стороне клиента: взять то, что файл несёт (имя материала + цвет),
и подобрать материал из своего каталога.

Хуже того — **цвет часто не значит ничего**: Revit кладёт цвет из «графики» семейства, а
не из appearance-ассета. Замер: `Walnut wood veneer (F900)` = rgb(127,127,127),
`Concrete, Cast-in-Place gray` = rgb(0,0,0), `Steel for furniture` = rgb(120,120,120).
Т.е. ореховый шкаф приезжает серым, бетон — чёрным. **Имя материала — более надёжный
сигнал, чем цвет.**

### 1.3. Когда стиля нет вообще (152 предмета)

Часть таких элементов имеет **связанный материал** (`IfcRelAssociatesMaterial`, в т.ч.
через тип — `IfcRelDefinesByType` → `IfcFurnitureType`), а цвет живёт не в `IfcStyledItem`
геометрии, а в `IfcMaterialDefinitionRepresentation` материала. Сейчас мы этот путь не
читаем — элемент приезжает серым. У части (кухонные шкафы, стиральная машина,
`AL_Table`) нет ни стиля, ни осмысленного материала — им остаётся **имя элемента**
(`FU Kitchen Cabinet`, `FU Washing Machine`, `Ikea_Hemnes_..._Shoe_Cabinet`) как последний
источник догадки.

Порядок источников (первый сработавший побеждает):

```
1. IfcStyledItem на самой геометрии          → цвет части (как сейчас)
2. IfcMaterial части/элемента                → имя → отделка из каталога (§3)
3. IfcMaterialDefinitionRepresentation       → цвет материала (новый путь)
4. имя элемента (эвристика, как LooksLikeScreen) → отделка
5. ничего не подошло                          → категорийный материал, как сейчас
```

Правило: **неизвестное имя не угадываем** — лучше честный цвет файла, чем «дуб» на
пластиковом стуле.

## 2. Части предмета (issue #126)

`ImportedMep` получает `Parts` — по одной на различный стиль, с собственным списком
треугольников поверх ОБЩЕГО списка вершин:

```csharp
public sealed class MepPart
{
    public string StyleName;        // "Textile - Leather - Black" — ключ сопоставления
    public string MaterialName;     // из IfcRelAssociatesMaterial, если есть
    public bool HasColor; public Color Color; public float Transparency;
    public List<int> Triangles = new();
    public SurfaceFinish Finish;    // подобранная отделка (§3) или None
}
```

- Части одного стиля внутри предмета **сливаются** (унитаз: 31 solid → 7 сабмешей).
- Нет стилей → ровно одна часть = сегодняшнее поведение (регресс исключён тестом).
- `ImportController` строит меш с `subMeshCount = Parts.Count` и массивом материалов;
  прозрачная часть (стекло телевизора, дверцы душевой) берёт стеклянный материал даже
  если элемент в целом непрозрачный.
- Плата — draw calls: считаем сабмеши импорта и пишем в лог; при переборе бюджета
  сливаем части ниже порога площади в основную.

## 3. Отделка по имени (issue #124) и каталог объектов (#128)

`Core/Ifc/IfcMaterialMap.cs` — чистая таблица подстрока → id отделки, без Unity:

```csharp
(  "oak|дуб|birch|берёз|natural wood",   "wood-oak"       ),
(  "walnut|орех|cherry|вишн",            "wood-walnut"    ),
(  "wenge|венге|black brown|stained",    "wood-dark"      ),
(  "leather|кожа",                       "leather-black"  ),
(  "textile|fabric|ткан|обивк",          "fabric-grey"    ),
(  "stainless|steel|сталь|металл|metal", "metal-brushed"  ),
(  "alumin|алюмин",                      "metal-aluminium"),
(  "plastic|пластик|полимер",            "plastic-white"  ),
(  "ceramic|керамик|эмаль|фаянс",        "ceramic-white"  ),
(  "concrete|бетон",                     "concrete-034"   ),
```

Стекло не одевается текстурой — у него свой материал (прозрачность из файла).

Каталог (`TextureDownloader.Curated`) получает новую категорию **`Objects`** — 30
CC0-материалов: дерево (дуб, орех, берёза, ясень, тик, тёмное, тёмный шпон), крашеная
панель, ткани (серая, синяя, зелёная, рогожка, войлок), кожа (чёрная, коричневая, белая),
металлы (шлифованный, полированный, алюминий, крашеный чёрный, латунь, медь), пластики
(белый, серый, чёрный), керамика, камень (терраццо, белый), ротанг и пробка. Тайлы —
**объектного масштаба** (дерево 0.4–0.8 м, ткань 0.4 м, пластик 0.3 м), не стенового.

Страховка: `SetupPaintTool` при сборке рига сверяет `IfcMaterialMap.AllFinishIds` с
каталогом и ругается ошибкой — опечатка в таблице ловится на Setup, а не в шлеме
неодетым шкафом (так и поймали не импортировавшуюся пробку).

В Paint эта категория — **отдельный таб** (дизайн-код 20: табы, а не длинный список), и
фильтр категорий (`design/04` §«Фильтр категорий») пускает таб `Objects` на
импортированные элементы и мебель каталога.

Применение — через существующую машинерию покраски (`Selectable.SetFinish` /
`PaintCommand`): одно место-писатель визуала, undo, персист как у любой другой отделки.

## 4. Развёртка запечённых мешей (issue #127)

У запечённых Brep-мешей **нет UV вообще** — текстура на них не ляжет. Генерируем
**метрическую box-проекцию** по правилу проекта «1 м мира = фиксированный кусок текстуры»
(`design/04`): для каждого треугольника берём доминирующую ось нормали и проецируем
позиции вершин на соответствующую плоскость в метрах. Меш из Brep уже несёт свои вершины
на грань, так что «расщепление» вершин почти не увеличивает счёт (контролируем ассертом).

Математика — в `RoomPlanner.Core` (`BoxUv.Project`), тест: площадь UV-треугольника равна
мировой (развёртка 1:1) на всех трёх осях — как `MetricUvTests` для стен.

## 5. Качество текстур (issue #129)

Сейчас скачивается **только `_Color.jpg`** (2K), настройки импорта дефолтные
(`compressionQuality: 50`, aniso 4, платформенных оверрайдов нет). Шейдер `LitVertexAO`
умеет `_BumpMap`/`_HasBump` с бестангентным TBN (design/22), но карту несёт только
запечённый ламинат.

Что делаем:

- Тянем `_NormalGL.jpg` из того же архива ambientCG, импортируем как `NormalMap`,
  кладём в `FinishLibrary.normalMaps` → рельеф получает **весь каталог**.
- **Нормали — 1K, цвет — 2K**: рельефу разрешение не нужно, а VRAM Quest'а — нужен
  (2K ASTC 6×6 ≈ 1.9 МБ против 0.5 МБ у 1K).
- Явные настройки импорта вместо дефолтов: Android-оверрайд ASTC 6×6,
  `compressionQuality` 100, aniso 8 для напольных (скользящие углы), мипы, sRGB —
  для цвета, линейно — для нормалей.
- Пишем в лог итоговый вес набора: бюджет должен быть виден, а не «как получилось».

## 6. Персист (issue #130)

Формат **v5**: `ProjectMep.Parts` (имя стиля/материала, цвет, прозрачность,
`ProjectFinish`, треугольники). Файлы v4 и старше читаются как одна часть — сегодняшний
вид. Тест: свежий импорт и загруженный проект визуально идентичны.

## 7a. Что получилось на реальном файле (замер после реализации)

`RoomPlanner → Analyze IFC Materials` (`RP_IFC=<файл>`, headless) на том же экспорте:

```
baked elements: 204, parts: 244, dressed by name: 140, nameless parts: 0
  1 part(s): 178 элементов
  2 part(s): 20
  3 part(s): 4
  7 part(s): 2        ← инсталляции унитазов
Wood - Stained → wood-dark (50×) · Clad - White → panel-white (24×)
IKEA natural wood → wood-oak (7×) · Walnut wood veneer → wood-walnut (6×)
Steel for furniture → metal-brushed (6×) · Glass → — (свой материал)
<Unnamed> → — (честный цвет файла, 98×)
```

Итог: **140 из 244 частей одеты каталогом**, 26 предметов перестали быть одноцветными,
а всё, чему имя ничего не сказало (98 безымянных материалов Revit + стекло), осталось со
своим цветом — как и требует правило «неизвестное не угадываем».

Побочные решения, которых не было в плане:

- **`Selectable.PaintAllSubmeshes`** — краска и подсветка обязаны накрывать ВСЕ сабмеши
  многочастного предмета; у стен/дверей осталось прежнее правило «только тело» (там
  сабмеш 1 — стекло, 2 — столярка).
- **Материалы частей создаёт `ImportController`** и он же их освобождает
  (`ReleasePartMaterials` при пере-импорте и в `OnDestroy`) — рантайм-материал не
  умирает вместе с объектом (правило 1.5). Кэш по ключу «шаблон+отделка+цвет»: на этаж
  ~40 материалов, SRP-батчер не давится.
- **Тайл и глянец берём из `FinishLibrary`**, а таблица имён знает только id отделки —
  одно место правды про масштаб текстуры.
- **Тинт только для «белых» материалов** (`Tintable`): «Пластик жёлтый» = белый пластик ×
  жёлтый, а орех, кожа и металл несут цвет в текстуре и цветом файла не красятся.

## 8. Осознанно откладываем

- **Свои текстуры из IFC4-файлов** (`IfcImageTexture`) — источников на руках нет; когда
  появятся, путь очевиден: текстура файла → `FinishKind.Texture` с внешним ассетом.
- **Покраска отдельной части** пальцем в сцене (сейчас отделка ложится на элемент
  целиком; части несут материалы файла) — до фидбека со шлема.
- **Атлас/texture array** для объектных материалов — пока число уникальных материалов
  мало, SRP-батчер справляется.
- **Наборы текстур вне APK** (как мебельные паки) — отдельная задача; каталог отделки
  пока ссылается сцена, значит он в APK.
