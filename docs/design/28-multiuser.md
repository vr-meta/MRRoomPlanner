# 27 — Мультиюзер: совместные сессии, голос, аватары 🔜

Совместное присутствие в проекте: хост создаёт сессию, остальные подключаются по коду,
все видят друг друга и вместе правят одну модель. Собственный сервер на **Rust** на нашем
VPS, **отдельный репозиторий** (`mrroomplanner-server`). Голос — в составе v1.

Принцип прежний: по сети ходят **параметрические данные и команды**, а не меши и не
текстуры. Это же делает свой сервер реалистичным: 6 участников — единицы КБ/с.

## 1. Два сценария

| | **Co-located** | **Remote** |
|---|---|---|
| Где люди | в одной физической комнате | в разных местах |
| Главная задача | совместить системы координат | передать модель помещения гостю |
| Риск | выравнивание, дрейф якорей | навигация гостя по чужой комнате |
| Очередь | после Remote (M7) | первым (M6) |

Remote даёт основную ценность («приходи посмотреть проект») без самой рискованной части,
поэтому идёт раньше. Co-located — надстройка: тот же транспорт, тот же лог команд, сверху
общий origin.

## 2. Архитектура: сервер обязан быть тупым

Доменная логика (стены, покраска, электрика, мебель) **не переносится в Rust** — это был бы
второй источник истины и вечная рассинхронизация с `RoomPlanner.Core`. Сервер знает только
три вещи:

1. **Упорядоченный лог команд.** Клиент шлёт непрозрачный `Vec<u8>`, сервер присваивает
   монотонный `seq`, кладёт в лог и рассылает. Что внутри — знает только C#.
2. **Реле поз.** Позы не логируются, не подтверждаются, теряются без последствий:
   широковещание последнего состояния на фиксированном тике.
3. **Сессии и права.** Создать/войти/участники/роль; единственное «доменное» знание —
   флаг «команда мутирующая» в конверте, чтобы отсечь `viewer`.

Следствие: новый инструмент в приложении **не требует правок сервера**.

```
Клиент (Unity/C#)                         VPS (Rust)
─────────────────                         ──────────
POST /v1/sessions             ──────────▶ code=K7M2QX, pin=4821, token
POST /v1/sessions/{code}/join ──────────▶ проверка pin → token (HMAC, TTL)
WS   /v1/rt?token=…           ◀────────▶ сессия
   ├─ команды  (надёжно, seq)              log: Vec<(seq, sender, blob)> + snapshot
   ├─ позы     (лоссиво, 20 Гц)            broadcast-тик, один бандл на клиента
   └─ контроль (join/leave/role/ping)
LiveKit (self-hosted, тот же VPS) ◀─────▶ голос (WebRTC), комната = код сессии
```

## 3. Репозиторий сервера

Отдельный репо `mrroomplanner-server` (Rust, лицензия как у основного проекта):

```
crates/protocol/   # типы сообщений + кодек + версия протокола (без tokio)
crates/server/     # axum + tokio: HTTP-эндпоинты, WS, сессии, тик
crates/loadtest/   # N ботов: позы + команды, для замеров
protocol/PROTOCOL.md          # ИСТОЧНИК ИСТИНЫ по формату
protocol/fixtures/*.hex       # золотые векторы (см. §4.4)
deploy/            # systemd unit, Caddyfile, docker-compose для LiveKit
```

**Дисциплина двух репо.** Формат живёт в `PROTOCOL.md`, клиентское зеркало — в
`Assets/RoomPlanner/Scripts/Core/Net/`. Чтобы зеркало не разъезжалось:

- `PROTOCOL_VERSION` — константа в обоих репо, сверяется в `Hello`; несовпадение мажора →
  сервер отвечает `ProtocolMismatch` с человекочитаемой причиной (клиент показывает
  «обнови приложение»), а не рвёт соединение молча;
- **золотые векторы**: `protocol/fixtures/*.hex` — заранее закодированные сообщения,
  закоммичены в оба репо; Rust-тест и C#-тест декодируют одни и те же байты и сверяют
  поля. Разъехался формат — красный тест с обеих сторон.

## 4. Протокол

### 4.1 Транспорт

v1 — **один WebSocket поверх TLS** (`wss://`). Причины: `ClientWebSocket` работает на
IL2CPP/Android без плагинов; в Rust — `axum` + `tokio-tungstenite`; один порт; Android
по умолчанию режет cleartext, TLS всё равно нужен.

TCP даёт head-of-line blocking. На 20–30 Гц мелких пакетов это не заметно, но транспорт
прячется за `INetTransport`, и если замеры на устройстве покажут джиттер поз > 30 мс —
добавляется **второй канал UDP только для поз** правкой одного класса. QUIC не берём:
зрелого C#-клиента под IL2CPP/Android нет (`System.Net.Quic` тянет нативный msquic).

Фреймы бинарные, первый байт — тип сообщения.

### 4.2 Сообщения

Клиент → сервер:

| Код | Имя | Содержимое |
|---|---|---|
| `0x01` | `Hello` | protocolVersion, appVersion, displayName, color |
| `0x10` | `Pose` | набор поз (§4.3), 20 Гц |
| `0x20` | `CommandSubmit` | clientSeq, mutating: bool, payload: bytes |
| `0x21` | `SnapshotOffer` | baseSeq, payload (только host) |
| `0x30` | `Ping` | t0 |
| `0x40` | `SetRole` | participantId, role (только host) |

Сервер → клиент:

| Код | Имя | Содержимое |
|---|---|---|
| `0x81` | `Welcome` | selfId, role, участники, logSeq, hasSnapshot |
| `0x82` | `Participant` | joined / left / renamed / roleChanged |
| `0x90` | `PoseBundle` | tick + позы всех остальных одним пакетом |
| `0xA0` | `Command` | seq, senderId, payload |
| `0xA1` | `CommandRejected` | clientSeq, причина (нет прав / лимит / протокол) |
| `0xA2` | `CatchUp` | чанк снапшота или чанк лога (late join) |
| `0xB0` | `Pong` / `SessionClosed` | t0, причина закрытия |

Позы **агрегируются**: один бандл на клиента за тик, а не эхо каждого сообщения.

### 4.3 Упаковка позы

- позиция — `i16` в **миллиметрах** относительно origin сессии (±32.7 м на ось; для
  зданий больше — ребейз origin, вынесен в отложенное §12);
- ориентация — smallest-three кватерниона, 4 байта;
- итого 10 байт на позу; голова + 2 кисти + точка указки + байт флагов (триггер, id
  активного инструмента) ≈ **40 байт на участника**.

Оценка: 6 участников × 40 Б × 20 Гц ≈ **5 КБ/с** нисходящего на клиента. Голос — на порядок
больше, и это ожидаемо.

### 4.4 Совместимость

Мажор протокола ломает, минор — нет: неизвестные типы сообщений и хвостовые поля
игнорируются обеими сторонами. Правило проверяется тестом на golden-фикстурах.

## 5. Сессии, вход, безопасность

- **Код сессии** — 6 символов Crockford base32 (без `I`, `L`, `O`, `U`), генерирует сервер.
  Энтропия ≈ 10⁹.
- **PIN** — 4 цифры, отдельным полем (не смешивать с кодом: набирать текст в шлеме больно).
- Пароль проверяется **один раз** при `join` → короткоживущий HMAC-токен; в каждом пакете
  пароль не гоняется. Реконнект — по тому же токену, пока не истёк.
- Лимиты: ≤ 8 участников, TTL сессии 12 ч простоя, блокировка кода после 5 неверных PIN,
  rate-limit на `CommandSubmit` и на `join`.
- Роли: `host` / `editor` / `viewer`. Проверка прав — **на сервере**: иначе `viewer` просто
  отправит команду напрямую.
- PII не храним: имя участника — что ввёл; логи без содержимого команд.
- TLS — Caddy перед сервером (или rustls внутри); деплой — один бинарь + systemd.

## 6. Клиентская сторона (Core)

Всё, что можно, — в `RoomPlanner.Core` (юнит-тестируемо, без Unity-зависимостей):

```csharp
// Core/Net/
interface INetTransport { void Connect(...); void Send(ReadOnlySpan<byte> data);
                          bool TryReceive(out Frame f); void Close(); }
//   App-реализация — ClientWebSocket; в тестах — LoopbackTransport (две стороны в памяти).

static class PoseCodec        // Pack/Unpack, roundtrip-тесты, ноль аллокаций
class  PoseInterpolator       // буфер + фиксированная задержка ~100 мс, экстраполяция ≤ 2 тика
class  NetSession             // конечный автомат: Idle→Joining→CatchUp→Live→Reconnecting
class  NetLog                 // применение по seq, дедуп, ожидающие локальные команды
static class CommandCodec     // TypeId → фабрика; реестр реплицируемых команд
```

### 6.1 Реплицируемые команды — главный рефакторинг

Сейчас `ICommand` (`Core/ICommand.cs`) держит **живые ссылки на объекты сцены** — по сети
такое не отправить. Вводится надстройка, старый интерфейс не ломается:

```csharp
interface IReplicableCommand : ICommand
{
    string TypeId { get; }              // "wall.add", "paint.room", "furn.move"
    void Write(IBufferWriter<byte> w);  // только стабильные Id + параметры
}
// CommandCodec.Read(TypeId, bytes, SceneModel) → ICommand
```

Требования:

- **стабильные Id у всех объектов сцены.** Сейчас Id есть у части типов (например
  `ProjectFixture.Id`); нужен сквозной `string Id` в `SceneModel` для стен/полов/проёмов/
  мебели/измерений и его сохранение в персисте (bump `ProjectData.CurrentVersion`);
- команда не смотрит на локальное состояние (выделение, активный инструмент) — только
  на свои поля;
- Id новых объектов генерирует **отправитель** (GUID-подобный), не сервер, — иначе
  оптимистичное применение невозможно.

**Оптимистичное применение:** локально команда применяется сразу, уходит на сервер и ждёт
подтверждения. Пришла чужая команда с меньшим `seq` — локальная откатывается, чужая
применяется, локальная переприменяется поверх (rebase). Пришёл `CommandRejected` — откат
и хаптика отказа.

**Undo в сессии:** отменяем **только свои** команды, и отмена уходит в сеть как новая
обратная команда (а не как «выкинуть seq N» из общего лога). Так все клиенты остаются
детерминированными, а чужой undo не выдёргивает объект у вас из рук.

### 6.2 Late join

Новый участник получает `logSeq` в `Welcome`, затем `CatchUp`: снапшот (если хост его
загружал) + команды после его `baseSeq`. Проигрывает локально → в актуальном состоянии.
Компакция: хост раз в N команд (или по запросу сервера) присылает `SnapshotOffer` —
это **тот же формат персиста** `ProjectData`, сервер хранит его непрозрачным блобом.

## 7. Аватары и присутствие

v1 — **без Meta Avatars SDK**: голова + две кисти + короткий «намёк на торс», цвет
участника, ник над головой (гаснет дальше 4 м). Дёшево, не тянет платформенный SDK,
читается отлично.

Что для обсуждения важнее красоты аватара:

- **луч-указка** каждого участника (чужой — тоньше и полупрозрачный);
- **курсор инструмента** и подсветка того, что человек держит/тянет;
- индикатор «говорит» на аватаре.

Интерполяция — фиксированная задержка ~100 мс, экстраполяция не более 2 тиков (иначе
руки «уезжают»). Ноль аллокаций в пер-кадровом пути (правило из дока 12).

## 8. Голос

**Self-hosted LiveKit** на том же VPS (open-source SFU, написан на Rust, есть Unity-клиент).
Причина: писать своё — это Opus, jitter-буфер, эхоподавление, микширование и отладка
«почему у одного скрежет»; по трудозатратам сравнимо со всем остальным сервером.

- комната LiveKit = код сессии; JWT для неё выписывает **наш** сервер при `join`
  (у него API key/secret) — пользователь вводит только код и PIN;
- пространственный звук: удалённый трек вешается на `AudioSource` в голове аватара;
- push-to-talk по умолчанию, плюс mute-тумблер и индикатор на аватаре;
- TURN нужен (встроенный в LiveKit либо coturn) + сертификаты;
- разрешение `android.permission.RECORD_AUDIO` и запрос в рантайме.

**Риск, проверяемый рано (M3):** работоспособность Unity-клиента LiveKit на Quest/Android
IL2CPP (WebRTC-плагин, стриппинг — грабли те же, что были с glTFast). Если не поедет —
фолбэк: сессии без голоса + внешний войс-чат; остальные вехи это не блокирует.

## 9. Выравнивание координат (co-located)

По убыванию «правильности»:

1. **Shared Spatial Anchors (Meta XR SDK)** — штатный путь, но требует App ID,
   entitlement-проверки, Data Use Checkup и зависит от версии Horizon OS (сверять с
   актуальной докой на момент реализации). **Отложено за пределы v1.**
2. **Матчинг геометрии комнат — основной механизм v1.** У нас уже есть параметрическая
   модель помещения: два шлема, отсканировавшие одну комнату, дают два набора углов и
   стен. `Core/Net/RoomAlign`: дескриптор угла (величина угла + длины смежных стен) →
   кандидатные пары → RANSAC → уточнение методом наименьших квадратов. Ищем **жёсткое 2D-
   преобразование** (yaw + XZ), Y берём из уровня пола. Чистая математика → тесты headless
   на синтетических комнатах с шумом и частичным перекрытием.
3. **Ручные 2 точки** — оба по очереди тыкают в один физический угол. Аварийный фолбэк,
   обязателен: спасает демо, когда всё остальное не сошлось.

Дрейф: за 20-минутную сессию позиции разъезжаются на сантиметры → периодический тихий
re-align по той же геометрии + кнопка «Re-align» на странице сессии.

## 10. UI

**Мультиюзер — не инструмент.** Все 12 слотов радиала заняты (оба резерва расписаны под
Furniture и Plumbing), а слот-таблица зафиксирована навсегда — поэтому сессия живёт
**страницей** рядом со страницей Rendering (шестерёнка на снап-полосе), по образцу
страниц Rendering / Projects.

Страница `Session`, только виджеты `SettingsSchema` v2 (док 20):

| Ряд | Виджет | Назначение |
|---|---|---|
| `Header` | — | «Session» |
| `Readout` | код сессии | крупно, чтобы продиктовать голосом |
| `Action` | Create / Join | Join открывает ввод кода + PIN |
| `Numeric` | PIN | 4 цифры |
| `Toggle` | Microphone | + индикатор push-to-talk |

| `Action` | Re-align | co-located |
| `Action` | **Leave session** | `destructive: true` + hold 0.5 с |
| `Progress` | Catching up… | проигрывание лога при входе |

- Иконки (`Core/IconPaths.cs`, 24×24, заливки, evenodd, каждая с тестом): `users`,

- Токены: нужен новый акцент слоя `UiColors.LayerSession` (предложение — мятно-зелёный,

- Анти-паттерны §7 дока 20 — в силе; своих попапов и своей модальности не изобретаем.

## 11. Тестируемость

Headless (входит в `ci/run-tests.ps1`):

- `PoseCodec` — roundtrip, границы диапазона, точность после квантования;
- `PoseInterpolator` — потери пакетов, переупорядочивание, отсутствие аллокаций;
- `CommandCodec` — roundtrip каждой реплицируемой команды;
- `NetLog` — порядок, дедуп, rebase локальных команд, идемпотентность повторов;
- `NetSession` поверх `LoopbackTransport` — join / catch-up / реконнект / отказ по правам;
- `RoomAlign` — синтетические комнаты, шум, частичное перекрытие, честный отказ при
  несовпадении;
- golden-фикстуры протокола (общие с репо сервера).

В репо сервера: unit-тесты лога и сессий, интеграционный тест «сервер + N фейковых
клиентов», `loadtest` на 20 ботов.

Только на устройстве: качество голоса, ощущение задержки поз, читаемость аватаров и
указок на passthrough, реальное выравнивание в co-located. Эти пункты явно висят в
чек-листе как «проверка в шлеме».

## 12. Что осознанно откладываем

- Meta Avatars SDK (полные аватары) и лицевая анимация.
- Shared Spatial Anchors и платформенные приглашения/друзья.
- Видео, шаринг экрана, запись сессии.
- Хранение проектов на сервере (сервер держит только активную сессию).
- Веб-зритель без шлема.
- Больше 8 участников, шардирование, кластер.
- Ребейз origin для зданий больше ±32 м (пока `i16`-миллиметры).
- Пространственные комментарии/метки и жест «смотрите сюда».
