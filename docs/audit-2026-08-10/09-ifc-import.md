# Импорт IFC и экспорт — аудит и план

Код: `Core/Ifc/StepTokenizer.cs`, `Core/Ifc/StepFile.cs`, `Core/Ifc/IfcImporter.cs`
(~1285 строк), `Core/Ifc/ImportedBuilding.cs`, `Import/ImportController.cs`,
`Import/MepView.cs`.

## Текущее состояние (кратко)

STEP-парсер (юникод `\X2\`, ленивые аргументы, единицы из `IFCSIUNIT`); импорт:
этажи, стены (ось+толщина+высота), колонны (прямоугольные), плиты (экструзия и
Brep-площадки), проёмы с дверными свингами, лестницы (с нормализацией футов Revit),
мебель/сантехника/прокси/перила (Brep, экструзии с дырками профилей, mapped items
с осями), цвета и прозрачность из `IfcStyledItem`. Повторный Load заменяет прошлый
импорт; весь импорт — один undo; фильтр этажей; статус со счётчиками пропусков.

## Баги к исправлению

### Б1. `ProjectMep.Storey` не заполняется (P0/B6)
Поле объявлено и читается при загрузке, но `ProjectStore.Capture` его не пишет
(`ProjectStore.cs:101-108`) → после save/load фильтр этажей мёртв (всегда −1).

**Как должно работать:** `MepView` хранит свой `StoreyIndex` (импорт его знает),
Capture копирует. Заодно в формат v2 — `StoreyIndex` у стен/плит/лестниц (сейчас
теряется у всех, см. [12-persistence.md](12-persistence.md)). Плюс: список этажей
(`ImportedStorey`: имя, отметка) тоже в проект — иначе после загрузки ряд Storey
пуст даже с корректными индексами.

### Б2. Рекурсия Placement без защиты от циклов
Битый файл с циклической цепочкой `IfcLocalPlacement` = StackOverflow (не ловится
catch) вместо «parse error».

**Как должно работать:** множество «в обработке» (visited-set) в резолве placement;
цикл → запись бракуется со счётчиком, импорт продолжается. Тест: синтетический
fixture с циклом → импорт жив.

### Б3. Имперские единицы дают модель ×3.28 молча
`DetectUnits` понимает только `IFCSIUNIT`; `IfcConversionBasedUnit` (футы) →
множитель 1.0.

**Как должно работать:** минимум — детект `IFCCONVERSIONBASEDUNIT` по
`IfcMeasureWithUnit` (готовый множитель лежит в файле) — это дёшево; если не
распознали единицы вовсе → предупреждение в статусе «units unknown, assuming m».

## Развитие

### Р1. Асинхронный импорт с прогрессом
Сейчас `ReadAllText` + парс + сборка — синхронно в одном кадре: фриз на большом
файле, тип `Progress` в UI существует, но не подключён (единственный потребитель —
UiShots).

**Как должно работать:** фазы «read → index → parse entities → build scene» —
корутиной с time-slice ~8 мс/кадр (сборка сцены и так поэлементная); ряд Progress
в схеме Import («Importing… 62 %»), инструменты заблокированы на время импорта,
B — отмена с откатом построенного. Чистые фазы (парс) можно в Task-поток,
Unity-объекты — только в главном.

### Р2. Экспорт glTF (F6) — первый выход наружу
Из приложения сейчас нельзя вынести ничего, кроме своего JSON.

**Как должно работать:** Action «Export glTF» в Import (или в будущем меню
проекта): обход `SceneModel` → glTF 2.0 (`.glb`) в Download. Меши уже есть у
каждого view (стены с сабмешами, полы, лестницы, MEP, электрика); материалы —
baseColor из отделки/краски, текстуры отделки — в буфер glb. Писать свой
минимальный glTF-writer в Core (формат простой: JSON + бинарный буфер), с
round-trip-тестом чтением стороннего валидатора в CI. Кейс: показать модель
заказчику в любом вьювере/Blender.

### Р3. Честность пропусков
`IfcSpace`, `IfcBeam`, `IfcCovering`, `IfcRoof`, `IfcCurtainWall`,
`IfcFlowSegment` (трубы!), `IfcCableCarrierSegment` пропускаются **без счётчика** —
пользователь не знает, что модель неполная.

**Как должно работать:** инвентаризация по типам до импорта (индекс `type → [id]`
уже есть): всё, что имеет Representation и не обработано ни одним импортёром, —
в счётчик `SkippedOther` с топ-3 типов в статусе: «…(12 skip: 6 Beam, 4 Covering,
2 Roof)». Отдельно: `IfcFlowSegment`/`IfcCableCarrierSegment` — кандидаты на
запечённый импорт той же машинерией `BakedTypes` (трубы отопления/водопровода
видны — прямой запрос пользователя из I12).

### Р4. Дальний прицел
- **IFC round-trip (экспорт IFC)** — после формата v2 и glTF; писать стены/плиты/
  проёмы как `IfcWallStandardCase`/`IfcSlab`/`IfcOpeningElement` (параметрика у нас
  честная, это реально).
- **IFC4** — по первому реальному файлу; сейчас индексы аргументов зашиты под 2X3.
- DWG — не начинать (закрытый формат, смотреть DXF при запросе).

## Техдолг

- `IfcImporter.cs` 1285 строк — разрезать на `IfcGeometry` / `IfcRelations` /
  `IfcElements` (по образцу разрезания MeasureSetup).
- Доступ к аргументам по индексам без проверок → NRE с «parse error» без
  диагностики; обёртка `TryArg(i)` с именем сущности в сообщении.
- Три копии обхода shell→face→bound→loop (`BrepWorldMesh`, `BrepLocalPoints`,
  `BrepTopRing`) — свести к одному итератору.
- `Level` плиты из `world[0].z` — падает на наклонной плите; брать max по контуру
  с warning.
- Комментарий `AttachOpenings` («не режет проёмы») устарел — панелизация работает.
- Внутренние контуры граней Brep (`IFCFACEBOUND`) игнорируются — задокументировать
  как ограничение.

## Порядок работ

1. Б1 (Storey) — в составе формата v2.
2. Б2 (циклы) + Б3 (единицы) — маленькие фиксы с тестами.
3. Р3 (счётчики + трубы) — заметная честность за небольшую цену.
4. Р1 (асинхронность) — перед демо на больших файлах.
5. Р2 (glTF) — отдельная фича `/new-feature`.
